# T-039: `cargo xtask review`: the stated numbers confronted with the files that own them

- **Role:** interface
- **State:** to review
- **Depends on:** T-036

## Goal

`lint` checks the mechanical rules of `AGENTS.md`, `conformance` computes the values. Neither answers
the question an outside reader asks first: *do the figures written in the README, the specs and the
release notes still agree with the files that produce them?* The two external reviews of 2026-10-08
each spent their first hour answering it by hand, and found real drift (a "not implemented" row for
two-compartment models that had shipped; a status stamp and a case count left behind by the code; a
"9970 values" claim whose shape hid that the fit oracles covered one model).

Add `cargo xtask review [--strict]`, read-only, no file written:

1. `review-conformance-total`: the overall line of `docs/conformance.md` equals the sum of its three
   sections, and the two halves of the line agree.
2. `review-conformance-floors`: every case in the tables has a floor line and every floor line names a
   case, so the generated file stays whole.
3. `review-model-ids`: every model id of the registry has a conformance case, and every conformance
   case of the `pk1.`/`pk2.` form names a model of the registry. The inputs-to-refuse row
   (`pk2.* (inputs to refuse)`) is a pattern, not an id, and is excluded.
4. `review-versions`: `Cargo.toml` and `CITATION.cff` state the same version.
5. `review-specs-index`: every `specs/*.md` is named by `specs/README.md`.
6. `review-claims-checked`: the case and value counts the README states for the one-compartment and
   two-compartment model rows are checked against the models section of `docs/conformance.md`.
7. `review-specs-counts` (note): the "Which rules are settled" table of the README against the
   `- Status: <tag>` lines of each spec. The README counts them with `grep` and the tag convention is
   the reader's, so a difference is worth reading, not a contradiction.
8. `review-release-drift` (note): what changed under `docs/`, `specs/`, `oracle/scripts/` or in
   `README.md` since the last tag, so a claim covered by that tag is not read as a claim about `main`.
   The generated `oracle/expected/` tree is counted as one thing and excluded, or every oracle
   regeneration would drown the signal.

Output: one `file:line rule [fail|note] message` per finding, then a summary line; exit 1 on any
failure, and on a note under `--strict`. Every rule has a positive and a negative fixture test; the
whole run reads 749 files in under a second. The rules work on `lint::Tree`, so they are tested without
touching the file system.

## Allowed files

`xtask/`, `.github/workflows/ci.yml` (add the step), `README.md` (the build block), the card, `board/`.

## Thread

- **First real run, on this tree (2026-10-09):** 0 failures, 3 notes.
  - `review-specs-counts` — `specs/models.md`: the README table says `19 | 2 | 4 | 0`, the `- Status:`
    lines count `37 | 4 | 9 | 0`. The row predates the two-compartment rules (T-031/T-035). Not fixed
    here: the counts are the reader's, and the row is PR #1 territory.
  - `review-claims-checked` — on `main`, the README states 21 cases and 886 values for the
    one-compartment models and nothing for two compartments, so the two-compartment coverage added by
    T-033/T-034 is invisible in the table a reader checks. Fixed by PR #1
    (`docs/readme-verified-head`), which is why this task does not touch that row.
  - `review-release-drift` — 24 files under `docs/`, `specs/` or `oracle/scripts/` or in `README.md`
    changed after `v0.1.0`; 9 of them on the `docs/readme-verified-head` branch. A reader who opens
    the tag does not see the two-compartment work, and the release note says so.
