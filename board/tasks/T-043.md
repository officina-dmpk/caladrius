# T-043: release workflow: binaries attached to every version tag

- **Role:** contributor-dsh (DeepSeek Harness, deepseek-flash, driven headless by the orchestrator; same rules as any agent, reviewed by the orchestrator or the reviewer before merge)
- **State:** to review
- **Depends on:** T-028

## Goal

A tag `v*` currently publishes nothing but source. Add `.github/workflows/release.yml` (free GitHub Actions only, no paid service, no third-party action that needs a token beyond `GITHUB_TOKEN`):

1. Triggered on push of a tag matching `v*`. Jobs on `ubuntu-latest` and `windows-latest`: toolchain from `rust-toolchain.toml`, `cargo build --release -p caladrius -p caladrius-cli -p caladrius-mcp`, then one archive per platform (`caladrius-<tag>-x86_64-unknown-linux-gnu.tar.gz`, `caladrius-<tag>-x86_64-pc-windows-msvc.zip`) containing the three executables, `LICENSE-MIT`, `LICENSE-APACHE`, `README.md` and `docs/conformance.md`, plus a `SHA256SUMS` file.
2. A final job that creates or updates the GitHub release of the tag (the release for `v0.1.0` already exists with notes: the job must attach assets to an existing release without overwriting its notes; for a new tag it creates a draft release named after the tag with the notes left empty for the maintainer).
3. The workflow must not run the test suite again (CI already did on the commit) but must fail if any build fails. Keep it under 80 lines and readable. Pin action versions (`actions/checkout@v5`, `dtolnay/rust-toolchain@stable`, `Swatinem/rust-cache@v2`, `softprops/action-gh-release` pinned to a release tag, or the `gh` CLI preinstalled on runners with `GITHUB_TOKEN`). Prefer the `gh` CLI if it keeps the file shorter.
4. README: one line in the "Install" or build section pointing to the release assets ("prebuilt binaries for Linux and Windows are attached to each release"), nothing more.
5. Also bump `actions/checkout@v4` to `@v5` in `.github/workflows/ci.yml` (Node 20 deprecation annotation seen on every CI run).

Validate the YAML (a YAML parser, or `act --list` if installed; do not run the workflow). State in the card thread exactly how the release step behaves when the release exists versus not.

Work on a git branch `dsh/T-043` from `main`, commit there with a message starting with `T-043:`, and do NOT push and do NOT open a pull request: the orchestrator reviews the branch and merges it.
